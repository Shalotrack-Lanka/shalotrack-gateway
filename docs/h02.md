# H02 family (LK-GPS LK208 and the `*HQ,<id>,V1,...#` trackers)

**Status: implemented and unit/integration tested against real published
sample frames; NOT yet verified on a physical LK208.** It is off by default.
Verify the first unit end to end (section "First unit") before adding more.

## Why the LK208 is handled as "H02"

There is no vendor datasheet for the LK208 that we could obtain. The mapping
comes from two independent sources:

- the Traccar supported-devices list, which lists the LK-GPS LK208 under the
  **H02** protocol;
- the TrackerAX / GPSWOX device pages, which list it on their H02 port.

H02 is the protocol spoken by a large number of Chinese trackers (the
`*HQ,<id>,V1,...#` text frames), so this family makes the gateway
cross-compatible with many other units too. The parser, the framer and the test
frames were built from the reference decoder and the real captures in its test
suite. If the first physical unit disagrees with any of this, the real capture
wins: see "If the unit does not behave".

## What is supported

- Text frames (`*HQ,...#`) and binary frames (`$` + BCD), detected from the
  first bytes on the shared port.
- Position reports: `V1`, `V2`, `V4`, `V6`, `V8`, `VI1`, `V19`, `VP1`, and any
  other `V<n>` type that carries a position (stored, but the raw bytes are also
  kept and the type is logged as unknown).
- All three coordinate spellings seen in the wild (`ddmm.mmmm`, `-dd-mm.mmmm`,
  and digits with no decimal point).
- Heartbeat (`HTBT`, `V0`): echoed back, and marks the device alive.
- Acknowledgement of `V1` and `NBR` with the server clock, as the protocol
  expects (`*HQ,<id>,V4,V1,<yyyyMMddHHmmss UTC>#`).
- Cell-tower / status types (`V3`, `NBR`, `LINK`, `XT`, ...): the device is
  marked alive, no position is written.
- Positions go through the same single-statement write as every other family
  (`GpsTrackings` plus the live `CurrentLocations` row). Speed is stored in km/h.
- A report without a GPS fix, a fix at (0, 0), a fix outside physical bounds
  (speed over 300 km/h, latitude/longitude out of range) or a fix stamped more
  than `H02_MAX_FUTURE_SECONDS` (default 600) in the future is acknowledged but
  not stored.
- Unknown message types get no reply, and their raw bytes are
  always kept in `RawPackets` (`Parsed = false`) so a new firmware variant can
  be added from a real capture instead of a guess.

## What is not (yet)

- **Commands.** None are implemented for this family; `command_service`
  refuses to write to a non-GT06 socket, so the API answers `501`. Configure
  the unit by SMS.
- **Battery and signal** are not written (units differ between protocols).
- **Ignition and alarm events** (vibration, SOS, overspeed, power cut) are
  decoded but **switched off** until checked on a real unit, see
  `H02_STATUS_FLAGS` below. An LK208 is a battery-powered magnet tracker with
  no ignition wire, so the ignition bit may mean nothing on it.
- Satellite count: the protocol does not report one; stored as `0`.

## The identifier question (read this before ordering a batch)

H02 has **no login frame**. Every message carries the device id, and the first
message on a connection is treated as the login: the id is looked up in the
activation list (`SetupShalotrackDevices.ImeiNumber`), exactly like an IMEI for
the other families. An id that is not activated gets the connection closed with
no reply.

The catch: many H02 units send a **10-digit id**, not the 15-digit IMEI. We do
not yet know what an LK208 sends. Do not guess: find out first (it takes one
connection attempt, see "Probe a unit"). Two outcomes:

1. It sends the 15-digit IMEI: nothing to change anywhere. Register it as usual.
2. It sends a shorter id: the gateway log says so
   (`this unit reports a N-digit id, not a 15-digit IMEI`) and shows the whole
   first frame. Then the ERP needs a decision, below.

### Why the ERP is the blocker, and why not to just relax it

The gateway and the database accept any text id (`ImeiNumber` is a plain `text`
column, the gateway lookup is an exact match). The restriction is in the admin
portal, where "IMEI" is a 15-digit, Luhn-checked identifier in six places:
`AddDeviceController` and `DevicesImport` (`digits:15`),
`Route::pattern('imei', '[0-9]{15}')` in `AppServiceProvider`, `Input::imei`,
`ScanDeviceController` and `App\Support\Imei` (15 digits plus a Luhn check
digit). The supplier-delivery verification (`DeviceRegistrationService`) is keyed
on that same scanned IMEI. Loosening the rule for everything would
weaken those checks for every family to suit one model.

If outcome 2 happens, the clean design (not built, needs the owners' sign-off
because it spans the admin DB, the API/gateway DB and the activation sync) is:
keep the 15-digit IMEI as the one canonical key, add a separate optional
"tracker id" (the wire id) to `SetupShalotrackDevices`, capture it at
delivery scanning from the unit's label, and let the gateway match
`ImeiNumber = $1 OR TrackerId = $1`. Do not map by guessing (for example by a
suffix of the IMEI): ids that are not derived from the IMEI cannot be mapped
that way, and a loose match is an impersonation risk.

### Probe a unit before registering it

Enable the family (`ENABLED_PROTOCOLS=GT06,GPS103,H02`) and power the unit
without registering it. It is rejected, and one log line carries everything:

    REJECTED — ID not admin-activated: <id> from <ip> (... N-digit id ...)
      — first frame (text|binary, <type>): <the frame>

That tells you the form, the id, the message type and the status word from a
single attempt, with nothing written to the database.

### Trial-only shortcut for a unit with a short id

To test the gateway path end to end with a short-id unit **without touching ERP
validation**, a row can be inserted by hand into the gateway database's
`SetupShalotrackDevices` with the wire id as `ImeiNumber` and
`Status = 'Activated'`. First look at the table's columns and defaults:

    SELECT column_name, is_nullable, column_default
    FROM information_schema.columns WHERE table_name = 'SetupShalotrackDevices';

Fill every NOT NULL column. Limits, so nobody is surprised: this validates
login, acknowledgements and position storage, but the unit will not show up
properly in the portal (its pages and the activation flow require a 15-digit
IMEI), so it cannot be assigned to a vehicle through the ERP. Delete the row
afterwards. This is a test aid, not a way to run customers.

## Security notes

- The id is the only credential in this protocol. It is printed on the box, so
  it is not secret. This is the same weakness the GPS103 family has, and the
  controls are the same: the activation allowlist (unknown ids are dropped before
  anything is stored), one socket bound to one id (a message naming a different
  id on an authenticated connection is treated as spoofing and the connection is
  dropped), strict bounds on everything stored, a cap on unframed bytes
  (`H02_MAX_UNFRAMED_BYTES`) and the connection caps already in the gateway.
- All device input is parsed by pure functions that only ever raise their own
  error type (fuzz-tested), and log lines print untrusted input escaped and
  length-capped.
- **Known gap, gateway-wide (not H02-specific):** the abuse guard written on
  30 Oct (per-IP connection cap, IP block after 5 distinct unknown ids,
  pre-login deadline, per-connection packet budget) is **not in the gateway's
  `main`**: it exists only as unmerged local work. Until it is merged, nothing
  throttles repeated unknown-id attempts from one address, and each attempt costs
  a database lookup. That affects GT06, GPS103 and H02 equally; merge it and
  wire the H02 handler to it rather than building a second mechanism here.
- If the SIM provider offers a private APN or fixed source ranges for this
  fleet, restricting the gateway security group to them removes the main
  remaining risk (id guessing). That is an infrastructure decision, not code.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `ENABLED_PROTOCOLS` | `GT06,GPS103` | Add `H02` to accept these units: `GT06,GPS103,H02`. |
| `H02_SPEED_IN_KMH` | `false` | Speed is assumed to be in knots (the reference behaviour). If a real unit reads low by about 1.85 against the speedometer, set `true`. |
| `H02_STATUS_FLAGS` | `false` | Decode ignition and alarm bits from the status word. Turn on only after step 6 below. |
| `H02_MAX_UNFRAMED_BYTES` | `2048` | A text frame ends with `#`. More bytes than this without one and the connection is dropped. |
| `H02_MAX_FUTURE_SECONDS` | `600` | A fix stamped further ahead than this is not stored. |

The container start script is `gateway-user-data.sh` in the infrastructure
repo (add `-e ENABLED_PROTOCOLS=GT06,GPS103,H02` to the `docker run`). The
startup log prints `Protocols enabled: ...`. To roll back, remove `H02` from
the variable and restart: the family is then treated as unknown traffic.

## Device configuration

Point the unit at the same host and port as the other families (domain, TCP,
the NLB listener), with the SIM's APN. **Use the SMS command set from the
supplier's LK208 manual or datasheet.** We do not have it, and the commands
that circulate for other trackers differ by firmware: a wrong command can set
the wrong server or lock the unit out. Ask the supplier for:

- the SMS commands for APN, server address/port and reporting interval;
- confirmation that the unit uses the H02 text protocol over TCP;
- what identifier the unit reports (IMEI or a shorter device id).

## First unit

1. Register the id (the IMEI printed on the box, to start with) in
   `SetupShalotrackDevices` with `Status = 'Activated'`.
2. On the gateway set `ENABLED_PROTOCOLS=GT06,GPS103,H02` and, for the trial
   only, `RAW_PACKET_MODE=all` so every frame is kept. Restart.
3. Power the unit, wait for it to connect, then read the gateway log (if it
   was rejected, the `REJECTED` line holds the whole first frame). Check:
   the line `Device connected ... [H02]`, the line `H02 first message — ID: ...`
   (is the id the 15-digit IMEI, or something shorter?), and whether the frame is
   text (`*HQ,...`) or binary (`$...`).
4. If it was rejected as "not admin-activated", the id the log shows is what must
   be activated (see "The identifier question").
5. Check the position on the map against the unit's real location, and the
   timestamp (the device clock is taken as UTC). Move the unit and compare the
   speed with a known speed: if it reads low by about 1.85, set
   `H02_SPEED_IN_KMH=true`.
6. Only if you want ignition/alarms: trigger the vibration/SOS/power-cut
   behaviour on the unit, read the status word in the stored raw frames, confirm it
   matches the table in `parsers/h02_parser.decode_status`, then set
   `H02_STATUS_FLAGS=true`.
7. Send us (or keep) 10-20 raw frames from `RawPackets` (`ProtocolNumber = 'H02'`)
   and the log. If anything above was different from what is documented here,
   those frames are how the parser gets fixed. Then set `RAW_PACKET_MODE` back.

## If the unit does not behave

| Symptom | Likely cause |
|---|---|
| Log shows `Unrecognised protocol ... First bytes: ...` | The unit speaks something else, or `H02` is not in `ENABLED_PROTOCOLS`. The hex in the log is the first bytes; send it. |
| `REJECTED — ID not admin-activated` | The id is not in `SetupShalotrackDevices`, or is not the 15-digit IMEI (see the hint in the log line). |
| Connects, repeats the same frame every few seconds | It is not getting an acknowledgement it accepts: capture the frame and what it expects. |
| `Unknown H02 message type` | A type we have not seen. The raw bytes are stored; send them. |
| Position is on the map but speed is too low | Speed unit: set `H02_SPEED_IN_KMH=true`. |
| Position is mirrored (wrong hemisphere) | The hemisphere letters are honoured as sent; compare the frame with the real location. |
| Online but no positions | No GPS fix yet (`V` in the validity field). Take it outside. |

## Tests

```
python -m unittest discover -s test -p "test_h02*.py" -v
```

`test_h02_parser.py` decodes real published frames (text and binary, all three
coordinate spellings) against their published positions, checks that the binary
and text encodings of one position agree, and fuzzes the decoder.
`test_h02_server.py` runs the real server over sockets with the database
mocked. Neither replaces step 3 to 7 above.
